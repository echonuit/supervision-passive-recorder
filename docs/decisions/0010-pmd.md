# 0010. PMD pour l'analyse statique

Date : 2026-09-08
Statut : acceptée

## Contexte

Le dépôt ne contrôlait que la forme du code. Spotless impose le
formatage, la CI lance les tests, et c'est tout : rien ne signale une
méthode qui a doublé de taille, une classe qui fait le travail de trois,
une méthode privée devenue morte, un littéral recopié six fois.

L'équipe a peu pratiqué Java. C'est précisément le moment où un outil
qui nomme un défaut et suggère le remède vaut mieux qu'une remarque en
relecture, parce qu'il tombe à chaque commit et pas seulement quand un
relecteur attentif passe.

L'outillage de VigieChiro Companion, dont ce projet reprend le domaine,
utilise PMD de cette façon depuis longtemps.

## Décision

`maven-pmd-plugin`, avec un jeu de règles maison à la racine du dépôt
(`pmd-ruleset.xml`) : huit garde-fous de conception, chacun associé au
refactoring qui le résout. L'analyse porte aussi sur le code de test.
Elle est bloquante dans `./mvnw verify`, donc en CI.

Les seuils sont ceux de PMD par défaut. Un seuil ne se relève qu'au vu
d'un code précis qui le justifie, et ce dépôt de démarrage n'en contient
aucun.

## Options écartées

**Checkstyle** : porte surtout sur le style, que Spotless règle déjà
mécaniquement. Deux outils sur le même terrain, dont un qui reformate
tout seul, n'apporte que du bruit.

**SpotBugs** : cherche des fautes dans le bytecode, ce qui est
complémentaire plutôt que concurrent. Écarté pour l'instant parce que ses
messages supposent de savoir lire ce que le compilateur a produit :
mauvais premier outil pour une équipe qui débute.

**SonarQube** : demande un serveur à héberger et à maintenir. Hors de
proportion ici.

**Le jeu de règles complet de PMD** : plusieurs centaines de règles, dont
beaucoup contradictoires entre elles. Un déluge d'avertissements au
premier lancement apprend surtout à ignorer l'outil.

## Conséquences

Une violation casse le build. Elle se corrige : ni `@SuppressWarnings("PMD...")`,
ni `//NOPMD`. Si un seuil est vraiment inadapté, on le rediscute dans
`pmd-ruleset.xml`, avec l'exemple sous les yeux et la justification écrite
à côté du chiffre.

Le code de test est analysé lui aussi. Ce n'est pas gratuit : la première
violation rencontrée sur ce dépôt était un littéral répété quatre fois
dans un test. C'est voulu — un test est du code qu'on relit.

À surveiller : si les règles se mettent à gêner sans rien révéler, c'est
le jeu de règles qu'il faut réduire, pas l'outil qu'il faut désactiver.

## Comment on saura qu'elle est tenue

Écrire une classe en violation manifeste — méthode privée jamais appelée,
littéral répété quatre fois, quatre `if` imbriqués — et lancer
`./mvnw verify` : le build doit échouer en nommant les règles. Un build
vert avec un `target/pmd.xml` vide ne prouve rien, il peut aussi vouloir
dire qu'aucun fichier n'a été analysé.

Cette vérification a été faite à la mise en place : les trois violations
ont bien été détectées.
